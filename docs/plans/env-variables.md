# Plan - Variables d'environnement (V0.11.0)

## Objectif

Configurer des variables d'environnement depuis Cairn, partagées entre toutes les
instances d'un projet ou scopées à une instance, pour se passer du copier-coller d'un
fichier `.env` entre chaque nouvelle instance. La rétrocompatibilité est impérative :
un programme qui lit un fichier `.env` doit continuer à trouver les valeurs définies
dans Cairn.

## 1. Modèle de données

Une variable est déclarée dans un scope, et sa valeur est soit partagée, soit résolue
par instance.

```ts
type EnvScope = "global" | "project" | "instance";

interface EnvVariable {
  id: string;
  key: string;
  value: string;
  perInstance: boolean; // scopes global et project uniquement
  secret: boolean;      // masquage dans l'UI
  enabled: boolean;
}
```

Trois comportements couverts par un seul modèle :

| Déclaration | Valeur | Cas d'usage |
| --- | --- | --- |
| global / projet, `perInstance: false` | partagée | `DATABASE_URL` commun, clés d'API |
| global / projet, `perInstance: true` | déclarée au scope, valeur fournie par instance | `PORT`, base de données par worktree |
| instance | locale | test ponctuel |

Résolution en trois passes, dernier gagnant par nom de clé : global, puis projet, puis
instance. Une variable `perInstance` prend sa valeur dans les `overrides` du fichier
d'instance (clé = id de la variable) ; sans override elle est absente du jeu résolu.
Les variables `enabled: false` sont ignorées.

Les valeurs supportent l'interpolation `{{ instance.branch }}`, `{{ project.name }}`
etc. via le moteur existant de `utils/commands/command-variables.ts` (aucun nouveau
moteur de template).

Les clés préfixées `CAIRN_` sont réservées et refusées à la saisie, ce qui garantit
qu'aucune variable utilisateur n'écrase les variables injectées par les commandes.

## 2. Persistance

Chemins ajoutés dans `storage.rs` (jamais de chemin inline) :

```
~/.cairn/env.json                                                # global
~/.cairn/projects/{project-id}/env.json                          # projet + options fichier
~/.cairn/projects/{project-id}/instances/{instance-id}/env.json  # instance + overrides
```

Format de fichier :

```jsonc
{
  "variables": [ /* EnvVariable[] */ ],
  "overrides": { "<variable-id>": "valeur" },  // instance uniquement
  "writeEnvFile": true,                        // projet uniquement
  "envFileName": ".env",                       // projet uniquement
  "ignoredConflict": false                     // instance uniquement
}
```

Nouveau module Rust `src-tauri/src/commands/env_vars.rs`, calqué sur
`custom_commands.rs` :

- `get_global_env` / `save_global_env`
- `get_project_env` / `save_project_env`
- `get_instance_env` / `save_instance_env`
- `write_env_file` / `read_env_file` / `env_file_status` (voir section 3)

Enregistrement dans `lib.rs` et ré-export dans `commands/mod.rs`. Tous les champs en
`#[serde(default)]` pour ne jamais casser une config existante.

Côté frontend :

- `src/lib/services/env-service.ts` : seule couche appelant `invoke()`.
- `src/lib/stores/env.ts` : `globalEnv`, `projectEnv`, `instanceEnv`, écriture
  debouncée, sur le modèle de `stores/custom-command.ts`.

## 3. Rétrocompatibilité - matérialisation du `.env`

Deux mécanismes complémentaires, les deux nécessaires.

### a) Fichier `.env` généré dans le worktree

Écrit par Rust avec un en-tête marqueur :

```
# Generated by Cairn - edits are overwritten
```

Règles :

- Nom configurable par projet (`envFileName`, défaut `.env`) et flag `writeEnvFile`
  activé par défaut.
- Jamais d'écrasement aveugle : si un fichier existe sans le marqueur, on n'écrit pas
  et l'UI affiche un bandeau proposant « Importer et gérer » ou « Ignorer ». Le choix
  « Ignorer » est mémorisé par instance (`ignoredConflict`) pour ne pas réafficher le
  bandeau à chaque ouverture.
- Réécriture : à la création d'instance, à chaque modification de variable (debounce),
  et avant chaque lancement de commande, de terminal ou de l'agent.
- Ignore git : on interroge d'abord `git_check_ignore`. Si le chemin n'est pas déjà
  ignoré, la ligne est ajoutée à `info/exclude` du dépôt (local, jamais commité), et
  jamais au `.gitignore` versionné du projet. `info/` étant partagé entre le dépôt
  principal et ses worktrees liés, une seule écriture couvre toutes les instances.

### b) Injection dans l'environnement des process

Le fichier seul ne suffit pas : un `npm run dev` lancé depuis un terminal Cairn doit
voir les variables même sans `dotenv`.

- Terminaux : `terminal_create` accepte déjà un `env` ; il faut le passer aussi depuis
  `addTerminal` (terminaux ordinaires), et pas seulement depuis `addCommandTerminal`.
- Commandes : fusion dans `buildEnv(resolution)` de `command-variables.ts`. Les clés
  `CAIRN_*` étant réservées, aucune collision n'est possible.
- Agent : `claude_cli.rs` spawne `claude` sans environnement personnalisé. Ajout d'un
  paramètre `env` transporté par `send_message` puis `AgentProvider::send`, appliqué
  via `.envs(env)`.

## 4. Import / export

`src/lib/utils/env/env-file.ts`, pur et testé :

- `parseEnvFile(content)` : gère `export KEY=`, guillemets simples et doubles,
  échappements `\n` en double quote, valeurs multi-lignes, commentaires, lignes vides ;
  les clés invalides sont ignorées et remontées dans un compte-rendu.
- `serializeEnvFile(vars)` : quoting minimal, ordre stable.

Import (`EnvImport.svelte`, sur le modèle de `CommandImport.svelte`) : coller un blob
ou choisir un fichier via `@tauri-apps/plugin-dialog` (déjà en dépendance),
prévisualisation des clés détectées, choix du scope cible, gestion des collisions
(remplacer / ignorer). Un raccourci « importer le `.env` du worktree » est proposé
à la création d'une instance.

Export : dialogue `save()` puis écriture du fichier, plus un bouton copier. Trois
portées : résolu (global + projet + instance), projet seul, instance seule.

## 5. UI

Nouvelle vue `src/lib/components/env/EnvView.svelte`, plus `EnvEditor.svelte` et
`EnvImport.svelte`, structurée comme `CommandsView.svelte` : trois sections repliables,
Instance, Projet, Global. Chaque ligne affiche la clé (`selectable` + `CopyButton`), la
valeur masquée avec bouton révéler, les bascules `perInstance` et `enabled`, et les
actions éditer / dupliquer / supprimer. Un panneau « Résolu » montre le jeu final et
indique quel scope l'emporte pour chaque clé.

Accès par une carte « Environnement » dans `ToolsPanel.svelte` (entrée du tableau
`TOOLS` et branche dans `selectTool()` de `Workspace.svelte`).

Persistance de la vue, les quatre couches obligatoires :

1. `envActive` dans `stores/ui.ts`, union de `showTool` étendue à `"env"` ;
2. `envActive` sur `ProjectUiState` dans `services/ui-state-service.ts` ;
3. snapshot et restauration dans `stores/view-state.ts` ;
4. champ `#[serde(default)]` sur le `ProjectUiState` Rust, plus un
   `subscribe(() => persistUiState())` dans `+page.svelte`.

i18n : bloc `env.*` dans `en.ts` et `fr.ts`. États d'attente en `Spinner` /
`Skeleton`, jamais de texte « Chargement ».

## 6. Tests

- `env-file.test.ts` : parsing (quotes, multi-lignes, `export`, commentaires, clés
  invalides) et aller-retour de sérialisation.
- `env-resolve.test.ts` : précédence global / projet / instance, `perInstance` sans
  override, variables désactivées, interpolation.
- Rust : écriture atomique, idempotence de `write_env_file`, refus d'écraser un
  fichier dépourvu du marqueur.

## 7. Hors périmètre

Les valeurs sont stockées en clair dans `~/.cairn/`, comme le reste des données de
l'application. Pas de chiffrement ni de trousseau système dans cette version : le
drapeau `secret` ne fait que masquer la valeur à l'écran.
